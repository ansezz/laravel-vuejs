You want login, registration and password reset for a Vue app without a second auth stack. Here is when Fortify is the right install, and what to edit instead when it isn't.

<TLDR
  audience="Laravel + Vue developers adding or customizing auth"
  learn={['Where the starter kit already uses Fortify', 'How a separate Vue SPA posts to Fortify endpoints', 'What to customize, and where']}
  applies="Laravel 13 · Fortify · Sanctum · Vue starter kit"
>

- The Vue starter kit already ships Fortify: edit `app/Actions/Fortify/*`, not a second login route.
- A separate SPA: install Fortify, set `views` to `false`, post to `/login` after `GET /sanctum/csrf-cookie`.
- Fortify on a SPA is the session cookie, not a bearer token.
- Turn features on and off in `config/fortify.php`.

</TLDR>

Search results for "Laravel Fortify Vue" still start with `composer require laravel/fortify` on top of Breeze. The current Vue starter kit already did that work. Login, registration, password reset, and email verification are Vue pages, and the actions that write the user live in `app/Actions/Fortify`. Installing Fortify a second time does not give you a better login form.

Use this page in two cases. You are changing those actions. Or the browser is a separate SPA and Fortify should expose the auth endpoints without rendering views. The cookie, the CSRF call, and CORS are [Sanctum for a Vue SPA](/laravel-sanctum-vue-spa). Which front end you are building is [Inertia, a SPA, or Nuxt](/laravel-vue-in-2026). GitHub as the only login is [Socialite](/laravel-socialite-vue).

## Case 1: the starter kit

Open `app/Actions/Fortify/CreateNewUser.php` when registration needs another column. The `create` method already validates name, email, and password. Add the column to that array and to the `User::create` call. Do the same kind of edit in `ResetUserPassword` when the reset rules change.

The Vue pages are under `resources/js/pages/auth`. They post to Fortify. You do not register a second `POST /login`.

The full route list, including two-factor routes this page does not copy, is in the [Fortify docs for Laravel 13](https://laravel.com/framework/docs/13.x/fortify).

## Case 2: a separate SPA

Fortify is the right install when Laravel is the API and Vue is another origin. The views stay off. The SPA renders the forms and posts to Fortify.

```bash
composer require laravel/fortify
php artisan fortify:install
php artisan migrate
```

```php title="config/fortify.php"
'views' => true, // [!code --]
'views' => false, // [!code ++]
```

With views off, Fortify does not try to return a Blade login page. These are the POST endpoints a first SPA usually needs:

- `/login`
- `/register`
- `/forgot-password`
- `/reset-password`
- `/email/verification-notification`

<TryIt title="See every route Fortify registered">

```bash
php artisan route:list --path=login
php artisan route:list --path=password
```

</TryIt>

<Callout type="heads-up" title="419, 422, and no bearer tokens">

Send them after `GET /sanctum/csrf-cookie`, with credentials, the same way the Sanctum guide posts `/login`. A 419 is still CSRF. A 422 is validation. Fortify's register endpoint returns validation errors for a duplicate email. Show `errors.email` from that JSON. Do not store a bearer token from these responses. Fortify's SPA story is the session cookie.

</Callout>

`POST /logout` is also Fortify's. Call it when the user signs out, then send them to the SPA's login route.

## What you customize

Features are flags in `config/fortify.php`, not extra packages. Registration, password reset, and email verification are already named there. Turn a feature off in that file rather than deleting a route by hand.

<Callout type="tip" title="one source of truth for password rules">

Keep password rules in `CreateNewUser` and `ResetUserPassword`. A Vue page that reimplements the same rules will drift. The server is the check that runs.

</Callout>

## Email verification

Enable `Features::emailVerification()` in `config/fortify.php`, then make the user model implement the contract. Without it, Fortify sends no verification mail:

```php title="app/Models/User.php"
use Illuminate\Contracts\Auth\MustVerifyEmail;

class User extends Authenticatable implements MustVerifyEmail
{
    // ...
}
```

Put `verified` middleware on routes that need a confirmed address. Unverified users are sent to the verification notice. The resend button posts to Fortify:

```ts
form.post('/email/verification-notification')
```

The link in the email is a signed URL that Fortify checks. Don't replace it with your own route that reads `?id=` and marks the user verified, and don't log the URL.

## Password reset

With `Features::resetPasswords()` on, Fortify handles two POSTs. The forgot form sends only `email`:

```ts
form.post('/forgot-password')
```

Fortify answers the same way whether the address exists or not, so the Vue page shouldn't say "we found your account". The emailed link opens the reset page with a `token` prop, and that form posts `token`, `email`, `password` and `password_confirmation`:

```ts
const form = useForm({ token: props.token, email: props.email, password: '', password_confirmation: '' })
form.post('/reset-password')
```

Errors come back on `form.errors.email` or `form.errors.password`.

## Confirm the password before a sensitive action

`password.confirm` middleware makes the user re-enter their password before a dangerous action, such as deleting the account:

```php
Route::delete('/account', [AccountController::class, 'destroy'])
    ->middleware(['auth', 'password.confirm']);
```

If they haven't confirmed recently, Laravel redirects to the confirm page. It posts one field, `password`, which is the current password:

```ts
form.post('/user/confirm-password')
```

The confirmation time is stored in the session and lasts `auth.password_timeout` seconds (3 hours by default). Don't track it in `localStorage`, and keep the middleware even if the Vue page already asked for confirmation.

## Log in with a username

Fortify looks users up by the `username` key in `config/fortify.php`, which is `email` by default:

```php title="config/fortify.php"
'username' => 'username',
```

The login form must then post a field with that same name, and errors come back under it:

```ts
const form = useForm({ username: '', password: '', remember: false })
```

Changing the label in Vue doesn't change the column Fortify queries. Accepting either email or username needs a custom `Fortify::authenticateUsing()` callback.

## Login rate limiting

Fortify throttles logins with the `login` limiter, which `FortifyServiceProvider` defines as 5 attempts a minute per username and IP:

```php title="app/Providers/FortifyServiceProvider.php"
RateLimiter::for('login', function (Request $request) {
    $throttleKey = Str::transliterate(Str::lower($request->input(Fortify::username())).'|'.$request->ip());

    return Limit::perMinute(5)->by($throttleKey);
});
```

Once it's hit, Fortify returns a validation error on the username field ("Too many login attempts…"), so the Vue form shows it like a wrong password. Keying on the username and IP together means one office behind a shared IP doesn't lock everyone out, and one attacker can't try a single account from anywhere unchecked.

## Where this stops

Fortify does not authorize "may this user edit this post". That is a [policy](/laravel-vue-policies) or a [permission](/laravel-vue-policies#roles-and-permissions-with-spatie). It also does not build the CRUD behind the login. That stays the [CRUD guide](/laravel-inertia-vue-crud).

## Recap

- The Vue starter kit is already Fortify; customize `CreateNewUser` and `ResetUserPassword`.
- Install Fortify yourself only for a separate SPA, with `views` off.
- Post after the CSRF cookie, with credentials. 419 = CSRF, 422 = validation.
- Authorization is a policy, not Fortify.
