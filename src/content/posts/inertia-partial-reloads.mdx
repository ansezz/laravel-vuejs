Your filter dropdown re-runs the expensive category query on every click. Your "load more" button replaces the list instead of growing it. Partial reloads fix both: ask Laravel for one prop, defer the slow ones, and append rows on demand.

<TLDR
  audience="Laravel + Vue developers using Inertia 3"
  learn={['`only` and `except` on `router.reload` and `<Link>`', 'Deferred props with the `<Deferred>` component', 'Load more with `Inertia::merge()`']}
  applies="Laravel 13 · inertia-laravel 3 · @inertiajs/vue3 3.9 · Vue 3.5"
>

- Wrap props in a closure, then `router.reload({ only: ['posts'] })` evaluates just that one.
- `Inertia::defer()` leaves a prop out of the first response and fetches it right after the first paint.
- `Inertia::merge()->append('data')` appends paginator rows, but only on partial reloads.

</TLDR>

A normal Inertia visit runs every prop on the page. Partial reloads exist so a filter, a poll, or a "load more" button does not redo the expensive ones. The visit has to target the page you are already on. A link to a different component always loads the full page.

The list those props come from is the [CRUD guide](/laravel-inertia-vue-crud). Counted pages versus cursors are [pagination](/laravel-vue-pagination). The app is [Inertia, a SPA, or Nuxt](/laravel-vue-in-2026).

## Reload one prop with only and except

Wrap props you can skip in a closure. Inertia evaluates the closure when that key is needed. A value computed before `Inertia::render` runs on every visit, including a partial one.

<CodeCompare before="Runs every visit" after="Runs when asked">

```php title="app/Http/Controllers/PostController.php"
return Inertia::render('posts/Index', [
    'posts' => Post::query()->latest('id')->paginate(10)->withQueryString(),
    'categories' => Category::query()->orderBy('name')->get(['id', 'name']),
]);
```

```php title="app/Http/Controllers/PostController.php"
return Inertia::render('posts/Index', [
    'posts' => fn () => Post::query()->latest('id')->paginate(10)->withQueryString(),
    'categories' => fn () => Category::query()->orderBy('name')->get(['id', 'name']),
]);
```

</CodeCompare>

Then ask for the one you need:

```vue title="resources/js/pages/posts/Index.vue"
<script setup lang="ts">
import { router } from "@inertiajs/vue3";

function refreshPosts() {
  router.reload({ only: ["posts"] });
}
</script>
```

`only: ['posts']` tells Laravel to skip `categories`. `except: ['categories']` is the same idea written the other way. A `<Link>` can do it without a function.

```vue title="resources/js/pages/posts/Index.vue"
<Link href="/posts?published=1" :only="['posts']">Published</Link>
```

<Callout type="heads-up" title="reloads, not form posts">

`:only` is a partial reload, not a partial form post.

</Callout>

Dot keys work for nested props. `only: ['auth.notifications']` reloads that nested value and leaves the rest of `auth` alone.

## Defer slow props until after the first paint

`Inertia::defer` leaves the prop out of the first response and fetches it immediately after the first paint. The Vue `<Deferred>` component renders the fallback until the key arrives. `#default="{ reloading }"` is how you dim the list during a later reload. `#rescue` renders when you passed `rescue: true` and the callback threw.

```php title="app/Http/Controllers/RoleController.php"
'permissions' => Inertia::defer(fn () => Permission::query()->orderBy('name')->get(), rescue: true),
```

```vue title="resources/js/pages/roles/Edit.vue"
<script setup lang="ts">
import { Deferred, router } from "@inertiajs/vue3";

defineProps<{
  permissions?: { id: number; name: string }[];
}>();
</script>

<template>
  <Deferred data="permissions" #default="{ reloading }">
    <template #fallback>
      <p>Loading permissions...</p>
    </template>

    <template #rescue="{ reloading }">
      <button
        type="button"
        :disabled="reloading"
        @click="router.reload({ only: ['permissions'] })"
      >
        Retry
      </button>
    </template>

    <ul :class="{ 'opacity-50': reloading }">
      <li v-for="permission in permissions" :key="permission.id">
        {{ permission.name }}
      </li>
    </ul>
  </Deferred>
</template>
```

<Callout type="gotcha" title="Deferred waits for a prop, not a URL">

`permissions` on that page is still a prop. `<Deferred>` does not fetch a URL you invent. It waits for the prop named in `data`.

</Callout>

### once() and WhenVisible

`->once()` on a deferred prop is remembered only while later pages still include that prop. A visit that leaves it out forgets the value, and the next page that includes it resolves the callback again. Reload that one prop when you need a fresh value sooner.

Inertia also ships `WhenVisible` for a deferred prop that should wait until the block scrolls into view. The prop name is the same contract. Use it for a block below the fold, not for the main list.

## Load more with Inertia::merge()

`Inertia::merge()` appends on a partial reload. A full visit replaces the prop even if you marked it for merging. The documented way to append a paginator's rows is `append('data')`.

```php title="app/Http/Controllers/PostController.php"
'posts' => Inertia::merge(
    fn () => Post::query()->latest('id')->paginate(10)
)->append('data'),
```

```ts title="resources/js/pages/posts/Index.vue"
function more() {
  router.reload({
    only: ["posts"],
    data: { page: props.posts.current_page + 1 },
  });
}

function search(value: string) {
  router.reload({
    only: ["posts"],
    data: { search: value, page: 1 },
    reset: ["posts"], // [!code highlight]
  });
}
```

<Callout type="gotcha" title="reset when the query changes">

Reset the prop when the search changes, or page two of a new query sticks to the end of the old rows.

</Callout>

Previous and Next links that replace the list, instead of appending, stay on the pagination page. `simplePaginate` is the right object when you do not want a total. Merge is the wrong tool for that footer.

<TryIt title="See what a partial reload sends">

Open the Network tab, click a link with `:only="['posts']"`, and look at the request headers: `X-Inertia-Partial-Data: posts` and `X-Inertia-Partial-Component` name the prop and the page. The JSON response holds only `posts`.

</TryIt>

## Prefetch the next page

Partial reloads make the current page cheaper. Prefetching makes the next one feel instant:

```vue
<Link href="/posts" prefetch>Posts</Link>
<Link href="/posts" prefetch="click">Posts</Link>
<Link href="/reports" prefetch cache-for="1m">Reports</Link>
```

By default, Inertia fetches the page after the pointer rests on the link for 75 ms and keeps the response for 30 seconds. `prefetch="click"` starts on mousedown. `prefetch="mount"` fetches as soon as the link renders. Use that only for the one link the user almost always clicks next.

A prefetch is a real `GET` to your controller. Only prefetch pages whose `GET` is safe to run on hover: no writes, no "mark as read". Never prefetch a logout or any other action. It also costs a request per hover, so leave it off long tables of links.

## Which tool for which job

| You want | Use |
|---|---|
| Refresh one prop (filter, poll) | Closure prop + `router.reload({ only })` or `<Link :only>` |
| Show the page fast, load a slow prop after | `Inertia::defer()` + `<Deferred>` |
| Load a block when it scrolls into view | `WhenVisible` |
| Append the next page of rows | `Inertia::merge()->append('data')` + `reset` on new searches |
| Replace the list with Previous/Next | Plain [pagination](/laravel-vue-pagination) |
| Push changes from the server | [Reverb](/laravel-reverb-vue) |

## Where this stops

Live updates from the server are [Reverb](/laravel-reverb-vue), not a timer that calls `router.reload`. A reload still asks Laravel. A broadcast pushes.

## Recap

- Closures make props lazy; `only`/`except` pick which ones run on a partial reload.
- Partial reloads only work on the page you are on.
- `Inertia::defer()` + `<Deferred>` shows a fallback, then the prop; `rescue: true` adds a retry slot.
- `Inertia::merge()` appends on partial reloads only; pass `reset` when the query changes.
