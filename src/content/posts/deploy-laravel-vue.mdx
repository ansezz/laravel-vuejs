Your app works locally, you deploy, and every page is a blank screen trying to load JavaScript from `localhost`. That's one stray file. Here is the whole deploy for a Laravel + Vue app, in order, with the traps marked.

<TLDR
  audience="Developers shipping a Laravel + Vue starter kit app"
  learn={['The build commands for every release', 'What must never reach the server', 'How SSR, the queue and migrations fit in', 'Trust proxies, database sessions and the /up health route']}
  applies="Laravel 13 · Vue starter kit · Vite · Laravel Cloud · VPS"
>

- Build: `composer install --no-dev`, `npm ci`, `npm run build` (or `build:ssr`), `php artisan optimize`.
- Never deploy `public/hot`. Set every `VITE_*` before the build.
- `php artisan migrate --force`; skip `storage:link` on Laravel Cloud.
- Production needs a supervised queue worker (and an SSR process if you use SSR).

</TLDR>

A Laravel and Vue app is one PHP app plus a Vite build. The mistake that takes sites down is shipping `public/hot`, which tells Laravel to load assets from the dev server. The rest is a short list.

This assumes the [Vue starter kit](/application-setup). A separate SPA from the [Sanctum guide](/laravel-sanctum-vue-spa) is two deploys: this one for the API, and the SPA host for the static files.

<Steps>

1. **Build** PHP and the assets.
2. **Cache** config, routes and views with `optimize`.
3. **Migrate** with `--force`.
4. **Keep** `public/hot` off the server.
5. **Run** the queue (and SSR) as long-lived processes.

</Steps>

## The build

[Laravel Cloud's deploy guide](https://laravel.com/cloud/docs/deploy-guides/laravel) uses this on every release:

```bash
composer install --no-dev
npm ci --audit false
npm run build
php artisan optimize
```

`npm run build` writes `public/build` and a manifest. Blade's `@vite` reads that manifest. `php artisan optimize` caches config, routes, and views into the release. Run it during the build, not after the release is already taking traffic.

<Callout type="gotcha" title="optimize freezes the environment">

`APP_ENV` must be `production` and `APP_DEBUG` must be `false` before `optimize`. A cached config file keeps whatever was in the environment at that moment. Change a key later and you need another `php artisan optimize`, or `php artisan optimize:clear` if you are debugging.

</Callout>

Then:

```bash
php artisan migrate --force
```

<Callout type="heads-up" title="storage:link on Cloud vs a VPS">

`--force` is required when `APP_ENV` is production. Do not add `storage:link` to a Cloud deploy. Cloud's disk resets on every deploy, so the symlink does not survive, and Cloud's own guide says to skip that command. User uploads on Cloud belong in the object storage bucket Cloud attaches. On a VPS, `storage:link` is once per machine when that machine serves the `public` disk from the [file upload guide](/laravel-vue-file-upload).

</Callout>

## Do not deploy the dev server

<Callout type="gotcha" title="public/hot">

Vite writes `public/hot` while `npm run dev` is running. If that file is on the server, every page tries to load JavaScript from your laptop's URL. Delete it. Do not commit it. The same goes for `node_modules`: install them in the build, then you only need the compiled files at runtime.

</Callout>

<TryIt title="A pre-deploy check">

```bash
test -f public/hot && echo "remove public/hot" || echo "ok: no public/hot"
test -f public/build/manifest.json && echo "ok: manifest built"
```

</TryIt>

Set every `VITE_*` variable before `npm run build`. Vite inlines them. A Reverb key added after the build does not show up until you build again. See the [Reverb guide](/laravel-reverb-vue).

## Server-side rendering

The Vue starter kit can render the first HTML on the server. Laravel Cloud says to swap the asset command when you want that:

```bash
npm run build:ssr
```

Use it instead of `npm run build` when those pages need server HTML. `npm run build` writes only the browser bundle and leaves `bootstrap/ssr` stale. Locally, `composer run dev` already server-renders. The current starter kit has no `dev:ssr` script. In production the SSR process has to stay up, the same way a queue worker stays up. Laravel Cloud and Forge both know how to keep that process running. On a VPS you supervise `php artisan inertia:start-ssr` yourself.

SSR is how a public Inertia page has HTML for a crawler before Vue boots. A logged-in app can ship the client bundle only. Pick that in [the stack guide](/laravel-vue-in-2026), not at the end of a deploy.

## The queue

Mail, broadcasts, and any `ShouldQueue` listener do nothing without a worker:

```bash
php artisan queue:work
```

`composer run dev` started one on your machine. Production does not.

| | Laravel Cloud | VPS |
|---|---|---|
| Queue worker | Managed, restarted on deploy | Supervise `queue:work`; run `queue:restart` after deploy |
| SSR process | Managed | Supervise `php artisan inertia:start-ssr` |
| `storage:link` | Skip (disk resets) | Once per machine |

 On a VPS, supervise `php artisan queue:work` and signal it with `queue:restart` after each deploy so it loads the new code. Cloud restarts its workers itself, so `queue:restart` is not a Cloud deploy command.

If you broadcast with Reverb, that is a second long-running process. The asset build does not include it.

## A VPS in one paragraph

Point the web server at the `public` directory. The front controller is `public/index.php`. PHP 8.3 or newer, the extensions in [the requirements](/requirements), and a database. Put `public/build` on disk, keep `public/hot` off disk, run migrations, and supervise the queue. That is the same app Cloud builds. The host is the part you are now operating yourself.

## Trust proxies so HTTPS sticks

The load balancer terminates TLS and forwards HTTP to PHP. Laravel then thinks the request is HTTP: generated URLs start with `http`, and `SESSION_SECURE_COOKIE` refuses to send the cookie. An infinite redirect, or a login that will not stick, is usually this, not a Vue bug.

On Laravel 11 and later, tell Laravel which proxies to trust in `bootstrap/app.php`:

```php title="bootstrap/app.php"
->withMiddleware(function (Middleware $middleware): void {
    $middleware->trustProxies(at: '*');
})
```

`at: '*'` is what the Laravel docs recommend when you are behind a cloud load balancer and do not know its IPs, such as AWS ELB. It is the right call when the app is only reachable through that balancer. It is the wrong call when the PHP process is on a public port, because a client can send `X-Forwarded-For` and `X-Forwarded-Proto` itself and Laravel will believe them.

If you know the balancer's addresses, pass them instead:

```php title="bootstrap/app.php"
->withMiddleware(function (Middleware $middleware): void {
    $middleware->trustProxies(at: [
        '192.168.1.1',
        '10.0.0.0/8',
    ]);
})
```

`APP_URL` should still be the `https` URL users type. Trusting proxies does not replace it.

<Callout type="gotcha" title="don't only force the scheme">

Do not set `URL::forceScheme('https')` and also forget the proxy. You can end up with https URLs and a request object that still says the scheme is http. Fix the forwarded headers first. I confirmed this in the lab: until `TrustProxies` is set, a request that arrives with `X-Forwarded-Proto: https` still reports `http` and `secure()` is false. After `$middleware->trustProxies(at: '*')`, the same request is https and `$request->ip()` is the client in `X-Forwarded-For`.

</Callout>

## Store sessions in the database

A file session lives on one machine's disk. The next request that lands on a different server, or on a platform that rebuilds the disk, cannot read it. The cookie is fine. The login looks like a 419.

Laravel 13 already defaults `SESSION_DRIVER` to `database`, and the default users migration creates the `sessions` table. On a fresh starter kit you are done. If you upgraded an older app, or you switched the driver back to `file`, create the table and set the driver:

```bash
php artisan make:session-table
php artisan migrate
```

```ini title=".env"
SESSION_DRIVER=database
```

Inertia visits then read the session from the database, including the CSRF token and the logged-in user. One database, many app servers. Redis is also fine when you already run it; the point is a store every server can reach. Feature tests in this lab use `SESSION_DRIVER=array` in `phpunit.xml`, which is the right non-persistent driver for the suite, not for production.

<Callout type="gotcha" title="deleting the sessions table logs everyone out">

Do not use the file driver on a platform that runs more than one machine, or that does not keep local disk. Do not treat "delete the sessions table to clean up" as a routine backup step unless you mean to log everyone out. That part is fine on purpose. Doing it in the middle of the day is the outage.

</Callout>

## 419 Page Expired after a deploy

A 419 is Laravel's `TokenMismatchException`. The CSRF token the browser sent doesn't match the one in its session. Inertia's HTTP client already reads the `XSRF-TOKEN` cookie and sends it as `X-XSRF-TOKEN` on every request, so you don't need a `csrf-token` meta tag. Inertia's docs ask Laravel apps to remove that tag, because a stale tag stops the token refreshing. When 419s start right after a deploy, the session is usually what changed:

- **The session store was wiped.** The `file` driver on a disk that is rebuilt on every release loses every session. Use `database` or `redis` in production. See [Store sessions in the database](#store-sessions-in-the-database).
- **`APP_KEY` changed.** Cookies are encrypted with it, so every cookie becomes unreadable. Keep one stable key per environment. When you rotate it, put the old key in `APP_PREVIOUS_KEYS`.
- **Cookie settings changed.** Check `APP_URL`, `SESSION_DOMAIN` (empty for a single host) and `SESSION_SECURE_COOKIE=true` behind HTTPS.

A session that simply expired still returns a 419, and Inertia shows a non-Inertia response in a modal. Inertia's docs recommend sending the user back with a message instead:

```php title="bootstrap/app.php"
use Symfony\Component\HttpFoundation\Response;

->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->respond(function (Response $response) {
        if ($response->getStatusCode() === 419) {
            return back()->with('message', 'The page expired. Please try again.');
        }

        return $response;
    });
})
```

Don't exclude the whole `web` group from CSRF checks, and don't add a wildcard CORS origin. A same-origin Inertia app doesn't use CORS at all.

## 409 means new assets

After a deploy, the first Inertia `GET` from an open tab carries the old `X-Inertia-Version`. inertia-laravel compares it with the current version (a hash of the Vite manifest by default). On a mismatch, it answers `409 Conflict` with an `X-Inertia-Location` header, and the client does a full page load to fetch the new JavaScript. The test for this setup confirms it: a stale `GET` gets the 409, while a stale `POST` is processed normally and redirects. Since Inertia 3.6, a background request such as polling doesn't force the reload. The next visit the user starts does.

The 409 is part of the protocol, not an error to handle in `onError`. Two things break it:

- **Every visit returns 409.** The version isn't stable. Usually `public/build/manifest.json` is missing on one server, or two servers behind one URL built different assets. Build once and ship the same `public/build` everywhere.
- **Your own `abort(409)`.** If a controller uses 409 to mean "this record changed", Inertia may read it as a version change. Report a stale edit as a validation error instead. The [CRUD guide](/laravel-inertia-vue-crud#stop-a-stale-edit-from-overwriting) shows how.

`Inertia::location($url)` uses the same 409 to send the browser to an external URL, such as an OAuth provider.
## Point the load balancer at /up

Laravel already registers a health route. In `bootstrap/app.php` it is:

```php title="bootstrap/app.php"
->withRouting(
    web: __DIR__.'/../routes/web.php',
    health: '/up',
)
```

`GET /up` returns 200 when the app boots without exceptions, and 500 otherwise. It does not render Inertia. Point the load balancer or the uptime monitor at that path, not at `/login` or `/`. A login page can return 200 while the app is too sick to serve a real request, and it can also return a redirect your probe treats as failure.

To add a deeper check, listen for `Illuminate\Foundation\Events\DiagnosingHealth` and throw if the database or cache is down. Laravel then turns that into a 500. In the lab, a listener that throws made `GET /up` return 500; without it the same route returned 200.

<Callout type="gotcha" title="the probe is not a user">

Do not add auth middleware to `/up`. Do not build a Vue dashboard as the health check. If you need a deeper check, keep it in that listener and keep the public body empty of secrets.

</Callout>

## Run migrations in the release, not in a request

The release already runs `php artisan migrate --force` in [the build](#the-build). `--force` is required when `APP_ENV` is production; it answers yes. Read the migration before you ship it. A `down()` that drops a column is not a small mistake.

Do not also run migrations from the app itself:

- Do not call `Artisan::call('migrate')` from a controller the Vue page can hit. Two deploys, or two curious browsers, should not race that.
- Do not migrate from a queued job "so the request stays fast". The new code and the old schema would be live together until the job runs.
- Do not wait for the first visitor so `AppServiceProvider` can migrate in `boot()`. Run the command in the release, before the new code serves traffic.

## Read config(), not env(), after optimize

`php artisan optimize` includes `config:cache`. That command bakes every `config/*.php` file into one cache and stops loading `.env` on each request or Artisan command. After that, `env('APP_NAME')` in a controller, a Vue prop, or any other app code returns `null`, unless the variable is set as a real system-level environment variable. `config('app.name')` still works, because the value was read from `.env` while the cache was built.

I confirmed this in the lab: a key that existed only in `.env` was visible to `env()` before `config:cache`, and `null` afterwards, while `config('app.name')` stayed the same.

Put a new key in a config file first:

```php title="config/services.php"
'maps_key' => env('MAPS_KEY'),
```

Then read `config('services.maps_key')`. Change `.env`, then run `php artisan optimize` again. Editing `.env` alone does nothing while the cache exists.

<Callout type="gotcha" title="don't cache config on your laptop">

Do not call `env()` in a Vue prop "just this once". Do not run `config:cache` or `optimize` in local development and then wonder why `.env` edits do nothing. Local should stay uncached. `php artisan optimize:clear` (or `config:clear`) drops the cache. The warning in [the build](#the-build) about freezing `APP_ENV` and `APP_DEBUG` is the same cache.

</Callout>

## Log a failure without the password

Production should write logs you can actually use, without putting secrets in `storage/logs`. The default channel is `stack`. `LOG_STACK=daily` rotates the file; `single` is one growing file. You can also stack `daily` and `slack` so a `critical` line pages the team and everything else stays on disk. Neither choice makes a password acceptable.

Log the fact, not the request body:

```php title="app/Http/Controllers/AuthenticatedSessionController.php"
use Illuminate\Support\Facades\Log;

Log::warning('login failed', [
    'email' => $request->string('email')->toString(),
    'ip' => $request->ip(),
]);
```

The second argument is contextual data, as the Laravel docs describe. Use a user id when you have one. Do not write `Log::debug($request->all())`. That is how the password, the CSRF token, the session id and the `Authorization` header land in the log file.

A Vue `onError` can show "Could not sign in". It should not `console.log` the form, for the same reason. The browser console is not private on a shared machine.

<Callout type="gotcha" title="don't ship logs to the page">

Do not send log lines to the Inertia page so an admin can read them in Vue. That is how a log viewer becomes a data leak. Telescope, local only, is the debugging tool.

</Callout>

## Recap

- One PHP app plus one Vite build.
- `optimize` after the environment is final. After that, read `config()`, not `env()`.
- No `public/hot`, no `node_modules` at runtime.
- Queue and SSR are processes you keep running.
- Trust the proxy so HTTPS and secure cookies stick. Store sessions in the database or Redis, not on one server's disk.
- Point probes at `/up`. Run migrations in the release, not from a Vue request. Do not log passwords.
- A 419 right after a deploy is usually the session store or `APP_KEY`. A 409 is Inertia fetching new assets.
