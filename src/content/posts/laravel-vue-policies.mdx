"Only the author can edit this post" sounds like one `v-if`. It is three pieces that have to agree: an owner column, a policy, and a controller that calls it. Here they are, plus the boolean that keeps the Vue link honest.

<TLDR
  audience="Laravel + Vue developers adding per-record authorization"
  learn={['How to add an owner column safely', 'How to write and call a policy', 'How to pass the same answer to the Vue page and test it']}
  applies="Laravel 13 · Inertia 3 · Vue 3 · Pest"
>

- Add `user_id`, set it from `$request->user()`, never from the request body.
- `PostPolicy::update` returns `$user->id === $post->user_id`; Laravel discovers it by name.
- The controller calls `$this->authorize('update', $post)`; the page gets `canUpdate`.
- Test with `assertForbidden()` on the endpoint.

</TLDR>

The posts in the [setup guide](/application-setup) have no owner. A policy needs one. This page adds `user_id`, then allows update only for that user. A permission such as "editor" is a different question and stays in [permissions](#roles-and-permissions-with-spatie). The screen is still the [CRUD guide](/laravel-inertia-vue-crud). The app is [Inertia, a SPA, or Nuxt](/laravel-vue-in-2026).

## The column

```php title="database/migrations/xxxx_add_user_id_to_posts_table.php"
Schema::table('posts', function (Blueprint $table) {
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
});
```

```php title="app/Models/Post.php"
public function user(): BelongsTo
{
    return $this->belongsTo(User::class);
}
```

<Callout type="gotcha" title="user_id never comes from the form">

Add `user_id` to `$fillable`, and set it in `store` from the logged-in user. Do not take `user_id` from the request body. The form would then let anyone assign the post to someone else.

</Callout>

```php title="app/Http/Controllers/PostController.php" {3}
Post::create([
    ...$data,
    'user_id' => $request->user()->id,
    'slug' => str($data['title'])->slug(),
    'published_at' => now(),
]);
```

## The policy

Laravel discovers `PostPolicy` for `Post` when the names match. You do not register it by hand.

```bash
php artisan make:policy PostPolicy --model=Post
```

```php title="app/Policies/PostPolicy.php"
public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}
```

<Callout type="gotcha" title="an empty method returns false">

`update` and `destroy` can share that line. `viewAny` can return `true` while the index is still a list of every post. Write the method you mean. An empty policy method that falls through to `false` hides every button and then looks like a Vue bug.

</Callout>

Call it from the controller. `authorize` throws 403 before the update runs.

```php
public function update(Request $request, Post $post): RedirectResponse
{
    $this->authorize('update', $post);

    // validation from the CRUD guide
}
```

Pass the same answer to the page. The link and the endpoint then agree.

<CodeCompare before="The page guesses" after="The policy decides">

```vue title="resources/js/pages/posts/Form.vue"
<Link v-if="post.user_id === $page.props.auth.user.id" :href="`/posts/${post.id}/edit`">Edit</Link>
```

```vue title="resources/js/pages/posts/Form.vue"
<Link v-if="canUpdate" :href="`/posts/${post.id}/edit`">Edit</Link>
```

</CodeCompare>

```php
return Inertia::render('posts/Form', [
    'post' => $post->only(['id', 'title', 'excerpt']),
    'canUpdate' => $request->user()?->can('update', $post) ?? false,
]);
```

```vue
<Link v-if="canUpdate" :href="`/posts/${post.id}/edit`">Edit</Link>
```

<Callout type="tip" title="per-row booleans on the index">

On the index, that boolean is per row. Compute it in the query's map or share a list of ids the user can edit. Do not ship every user's id to the browser and decide there.

</Callout>

## A test

<TryIt title="Prove the endpoint is closed">

```php title="tests/Feature/PostPolicyTest.php"
it('forbids a user who does not own the post', function () {
    $owner = User::factory()->create();
    $other = User::factory()->create();
    $post = Post::factory()->for($owner)->create();

    $this->actingAs($other)
        ->put("/posts/{$post->id}", [
            'title' => 'Taken',
            'excerpt' => 'Not yours.',
        ])
        ->assertForbidden();
});
```

</TryIt>

The factory needs `user_id` once the column exists. `assertForbidden` is the assertion that matters. A test that only checks the missing link does not close the endpoint.

## Where this stops

Spatie permissions and this policy can both exist. An editor permission can allow `update` even when the user is not the owner, inside the policy, with `$user->can('posts.update')`. Put that combination in the policy so there is still one method the controller calls. Do not check the role in the Vue page.

## Authorize in the controller

The policy only protects you if every request that changes data asks it. In Laravel 11 and later, the base `Controller` class is empty, so `$this->authorize()` doesn't exist unless you add the `AuthorizesRequests` trait yourself. Use the `Gate` facade instead:

```php title="app/Http/Controllers/PostController.php"
use Illuminate\Support\Facades\Gate;

public function edit(Post $post): Response
{
    Gate::authorize('update', $post);

    return Inertia::render('posts/Edit', [
        'post' => $post->only(['id', 'title', 'body']),
    ]);
}

public function update(UpdatePostRequest $request, Post $post): RedirectResponse
{
    Gate::authorize('update', $post);

    $post->update($request->validated());

    return to_route('posts.show', $post);
}
```

`Gate::authorize()` throws an `AuthorizationException`, which becomes a 403. Inertia shows its error page and the Edit component never mounts. Check `edit` and `update` separately: they're two different requests, and someone can send the `PUT` without ever opening the form. Policy methods should return `true` or `false`, not call `abort()`.

## Share the answer as a boolean

The Vue page can't run a PHP policy, so send the answer:

```php
return Inertia::render('posts/Show', [
    'post' => $post->only(['id', 'title']),
    'can' => [
        'update' => $request->user()?->can('update', $post) ?? false,
        'delete' => $request->user()?->can('delete', $post) ?? false,
    ],
]);
```

```vue
<Link v-if="can.update" :href="`/posts/${post.id}/edit`">Edit</Link>
```

Use `v-if`, not CSS, so the button isn't in the DOM. Don't send the user model or a list of every ability so the page can work it out: Vue can't see the policy anyway. The boolean is a snapshot from the last response, which is why the controller still checks.

## Gate the index with viewAny

An index has no single post to pass, so the policy uses `viewAny`, which receives only the user. Call it with the class name:

```php
public function viewAny(User $user): bool
{
    return $user->hasVerifiedEmail();
}

public function index(Request $request): Response
{
    Gate::authorize('viewAny', Post::class);

    return Inertia::render('posts/Index', [
        'posts' => $request->user()->posts()->latest('id')->paginate(12),
    ]);
}
```

Passing an instance would call `view` instead. `viewAny` answers "can this person open the list?". The query answers "which rows?". If users may only see their own posts, scope the query as well. Don't send every row and filter in Vue.

## Roles and permissions with Spatie

A policy answers "does this user own this post?". A permission answers "is this user an editor?". For the second, [spatie/laravel-permission](https://spatie.be/docs/laravel-permission/v6/introduction) is the common package:

```bash
composer require spatie/laravel-permission
php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"
php artisan migrate
```

```php title="app/Models/User.php"
use Spatie\Permission\Traits\HasRoles;

class User extends Authenticatable
{
    use HasRoles;
}
```

Give permissions from a seeder or an admin command, never from the Vue page:

```php
$user->givePermissionTo('posts.publish');
$user->assignRole('editor');
```

Spatie registers its permissions with Laravel's gate, so `$user->can('posts.publish')` works, and so does sharing it as a boolean the same way as above. Combine the two when you need both: `$user->can('posts.publish') && $user->can('update', $post)`. Don't turn "only the author" into another permission string. That rule needs the post, so it belongs in a policy.

## Permission middleware on the route

When a whole route is for one permission, refuse the request before the controller runs. Register the aliases in `bootstrap/app.php`:

```php title="bootstrap/app.php"
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'role' => \Spatie\Permission\Middleware\RoleMiddleware::class,
        'permission' => \Spatie\Permission\Middleware\PermissionMiddleware::class,
    ]);
})
```

```php title="routes/web.php"
Route::post('/posts/{post}/publish', PublishPostController::class)
    ->middleware(['auth', 'permission:posts.publish']);
```

A user without `posts.publish` gets a 403. Spell the permission the same way in the seeder and in the route, because `posts.publish` and `post.publish` are two different permissions. Laravel's own `can` middleware does the same for policies: `->can('update', 'post')`.

## Recap

- Owner column from the logged-in user, never from input.
- One policy method per ability; the controller calls it.
- The page receives the policy’s answer as a boolean.
- Combine permissions inside the policy, not in Vue.
