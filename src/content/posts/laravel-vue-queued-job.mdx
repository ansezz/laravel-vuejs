The user clicks Export, the page says "Done!", and the file doesn't exist yet. A queued job is a promise, not a result. Here is a status row Vue can read, a poll that stops itself, and a private download only the owner can open.

<TLDR
  audience="Laravel + Vue developers running slow work in the background"
  learn={['How to track a queued job with your own status row', 'How to poll from Vue with a partial reload', 'How to keep the result private and test it']}
  applies="Laravel 13 · Inertia 3 · Vue 3 · Pest"
>

- Create an `exports` row (`pending`), dispatch `BuildExport`, redirect to its page.
- The job writes to the private `local` disk and sets `ready`, or `failed` in `failed()`.
- Vue polls `router.reload({ only: ['export'] })` every 2s from `onMounted` while `pending`.
- Download through a controller that checks the owner; use a plain `<a>`.

</TLDR>

The page lies if it says "done" at the moment you dispatch. The job is a row in `jobs` until a worker runs it. Store your own status, return that row to Vue, and read it again until it leaves `pending`.

<Callout type="gotcha" title="stuck on pending">

If the status stays `pending`, nothing is processing the `jobs` table. `composer run dev` starts a queue listener with the app server. `php artisan serve` alone does not. Run `php artisan queue:work` in that case. The production worker, and `queue:restart` on deploy, stay in the [deploy guide](/deploy-laravel-vue).

</Callout>

A new Laravel app already ships the jobs migration and `QUEUE_CONNECTION=database`. Run `php artisan migrate` if that table is not in the database yet. Do not create a second jobs migration. This page is also not the posts CRUD. The row is an export. The stack is [Laravel and Vue in 2026](/laravel-vue-in-2026).

## The row and the job

```bash
php artisan make:model Export -m
php artisan make:job BuildExport
```

```php title="database/migrations/xxxx_create_exports_table.php"
Schema::create('exports', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->string('status')->default('pending');
    $table->string('path')->nullable();
    $table->timestamps();
});
```

`status` is `pending`, `ready`, or `failed`. `path` stays null until the file exists. Add `user_id`, `status`, and `path` to the model's `$fillable` array.

```php title="app/Jobs/BuildExport.php"
use App\Models\Export;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Storage;
use RuntimeException;
use Throwable;

class BuildExport implements ShouldQueue
{
    use Queueable;

    public function __construct(public Export $export) {}

    public function handle(): void
    {
        $path = 'exports/'.$this->export->id.'.csv';
        $stored = Storage::disk('local')->put(
            $path,
            "id,status\n{$this->export->id},ready\n",
        );

        if ($stored !== true) {
            throw new RuntimeException('Export file was not written.');
        }

        $this->export->update([
            'status' => 'ready',
            'path' => $path,
        ]);
    }

    public function failed(?Throwable $exception): void
    {
        $this->export->update(['status' => 'failed']);
    }
}
```

<Callout type="gotcha" title="private disk only">

`local` is the private disk. Do not write this file onto the `public` disk, and do not copy it under `storage/app/public`. The download below checks the owner. A URL that anyone can guess is not a check.

</Callout>

## Dispatch, then show the row

```php title="app/Http/Controllers/ExportController.php"
public function store(Request $request): RedirectResponse
{
    $export = Export::query()->create([
        'user_id' => $request->user()->id,
        'status' => 'pending',
    ]);

    BuildExport::dispatch($export);

    return to_route('exports.show', $export);
}

public function show(Request $request, Export $export): Response
{
    abort_unless($request->user()->id === $export->user_id, 403);

    return Inertia::render('exports/Show', [
        'export' => $export->only(['id', 'status', 'path']),
    ]);
}

public function download(Request $request, Export $export)
{
    abort_unless(
        $request->user()->id === $export->user_id && $export->status === 'ready',
        403,
    );

    return Storage::disk('local')->download($export->path);
}
```

Register those three routes behind `auth`. Name them `exports.store`, `exports.show`, and `exports.download`. `only` keeps the page props to the fields Vue prints. The path is not a public URL. The download action is the only way out of the private disk.

## The Vue page

Poll while the row is `pending`. `router.reload({ only: ['export'] })` is the same partial reload as the [partial reloads guide](/inertia-partial-reloads). Two seconds is enough to see the change without a websocket. Start the timer in `onMounted` and clear it in `onUnmounted`. Do not read `window` in setup. This page can be server-rendered.

```vue title="resources/js/pages/exports/Show.vue"
<script setup lang="ts">
import { onMounted, onUnmounted } from "vue";
import { router } from "@inertiajs/vue3";

const props = defineProps<{
  export: { id: number; status: string; path: string | null };
}>();

let timer: ReturnType<typeof setInterval> | undefined;

onMounted(() => {
  if (props.export.status !== "pending") {
    return;
  }

  timer = setInterval(() => {
    if (props.export.status !== "pending") {
      clearInterval(timer);
      return;
    }

    router.reload({ only: ["export"] });
  }, 2000);
});

onUnmounted(() => {
  if (timer) {
    clearInterval(timer);
  }
});
</script>

<template>
  <p v-if="export.status === 'pending'">Preparing the file.</p>
  <p v-else-if="export.status === 'failed'">The export failed.</p>
  <a v-else :href="`/exports/${export.id}/download`">Download</a>
</template>
```

<CodeCompare before="Treated as a page visit" after="A real download">

```vue title="resources/js/pages/exports/Show.vue"

```


</CodeCompare>

The download link is a normal anchor. An Inertia `<Link>` would try to treat the file as a page visit.

When the status should appear without a timer, replace the interval with the broadcast in the [Reverb guide](/laravel-reverb-vue). This page does not install Echo. The row you stored is still the source of truth. The broadcast only tells the browser to reload it.

## A test

```php title="tests/Feature/ExportTest.php"
use App\Jobs\BuildExport;
use App\Models\Export;
use App\Models\User;
use Illuminate\Support\Facades\Queue;

it('queues an export', function () {
    Queue::fake();

    $this->actingAs(User::factory()->create())
        ->post('/exports')
        ->assertRedirect();

    Queue::assertPushed(BuildExport::class);
});

it('marks the export ready', function () {
    $export = Export::query()->create([
        'user_id' => User::factory()->create()->id,
        'status' => 'pending',
    ]);

    (new BuildExport($export))->handle();

    expect($export->fresh()->status)->toBe('ready');
});
```

<TryIt title="Run it with and without a worker">

Start an export with no worker running and watch it sit on "Preparing the file." Then run `php artisan queue:work` in another terminal; within two seconds the page shows **Download**.

</TryIt>

`php artisan test --filter=ExportTest`. `Queue::fake()` proves the dispatch. Calling `handle()` proves the file write and the status change without a worker. The download test is the same ownership check as the controller: another user, and a row that is still `pending`, both receive 403.

## Run the queue worker

`composer run dev` already starts a queue listener with the app. That is the right process while you are changing a job class: `queue:listen` boots the framework for every job, so it picks up your edits. `php artisan serve` alone does not start a worker; in that case run `php artisan queue:listen` in another terminal.

In production, run the long-lived worker:

```shell
php artisan queue:work
```

`queue:work` boots once and does not see new code until the process restarts. On a VPS, `php artisan queue:restart` after deploy signals those workers to exit after the current job. Laravel Cloud restarts its workers itself, so `queue:restart` is not a Cloud deploy command. The [deploy guide](/deploy-laravel-vue) has the table.

<Callout type="gotcha">

Do not call `queue:work` from a controller so a Vue button "starts the worker". The button dispatches a job. A supervisor, or the platform, runs the worker.

</Callout>

`queue:listen` under systemd in production will work, slowly, because it reboots the framework for every job. Do not add it to a release because a forum post listed it.

## Show failed jobs to an admin

A new Laravel 13 app already has a `failed_jobs` table in `0001_01_01_000002_create_jobs_table.php`. You only need `php artisan make:queue-failed-table` on an older app that is missing that migration. Do not run the maker in a fresh app; you would add a second migration for a table that already exists.

`QUEUE_CONNECTION` has to be something that records failures. `sync` runs the job in the request and does not use this table.

This page already stores `failed` on your `exports` row in `failed()`. The `failed_jobs` table is the framework's copy: every failed job, including mail and broadcasts, with a payload and an exception. An admin page may show the safe columns:

```php
'failed' => DB::table('failed_jobs')->orderByDesc('id')->limit(20)->get(['id', 'uuid', 'failed_at']),
```

Retry from a command you trust, not from a public button:

```shell
php artisan queue:retry all
```

<Callout type="gotcha">

Do not put `payload` or `exception` in an Inertia prop. The exception text can include request data. Do not let every signed-in user open this list.

</Callout>

## Record when a schedule last ran

`php artisan schedule:list` prints the next due time. It does not store a last run. If an admin page must show "last ran", write a timestamp yourself from the command.

```php
use Illuminate\Support\Facades\Schedule;

Schedule::command('reports:daily')->daily()->withoutOverlapping();
```

`withoutOverlapping()` uses the cache so a slow run is not started twice. It is not a history table.

Inside the command, after the work:

```php
Cache::forever('reports.daily.last_run', now()->toIso8601String());
```

Share that string with the admin page. `forever` here means "until the next success overwrites it", not "keep a history".

<Callout type="gotcha">

Do not scrape the scheduler's mutex and show it as the last success. The mutex means "it is running or it crashed while holding the lock". Do not run `schedule:work` from the Vue page. The system cron runs `schedule:run` every minute, or the platform does.

</Callout>

## Prune old rows on a schedule

The `exports` table in this guide will grow. Prune a table you can afford to lose, such as expired exports or old invitations. Do not point that scope at `User`.

```php
use Illuminate\Database\Eloquent\Builder;
use Illuminate\Database\Eloquent\MassPrunable;

class Export extends Model
{
    use MassPrunable;

    public function prunable(): Builder
    {
        return static::where('created_at', '<=', now()->subDays(30))
            ->whereIn('status', ['ready', 'failed']);
    }
}
```

```php
Schedule::command('model:prune')->daily();
```

`MassPrunable` deletes in SQL and does not fire model events. Use `Prunable` when you need `deleting`. Run `php artisan model:prune --pretend` before you trust the scope. Something on the server has to call `schedule:run` every minute; the [deploy guide](/deploy-laravel-vue) is the release around that cron.

<Callout type="gotcha">

Do not prune from a Vue button that calls this on `User`. Do not write `where('created_at', '>=', ...)` and think you kept the old rows. That keeps the new ones and deletes the rest. Read the comparison twice.

</Callout>

## Recap

- Store your own status; the `jobs` table is not a UI.
- Poll with a partial reload and stop when the status changes.
- Private disk + owner check for downloads.
- `Queue::fake()` for the dispatch, `handle()` for the work.
- `queue:listen` locally, `queue:work` in production; Cloud restarts workers for you.
- Show only safe `failed_jobs` columns; write your own last-run stamp; prune tables you can afford to lose.
